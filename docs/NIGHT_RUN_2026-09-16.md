  records said "No cover, next working day".
* **BUG-614** — after the route finder stopped claiming route comparisons, they fell into the

* **BUG-616** — "longest unseen" was read off the interval column instead of being computed.
  Where a register records a last-something date and an interval, the system now computes the

## The morning's finding: the provider was crashing, not the prompt

The continuity question reached the right register and still fell back to *"I found 12 records
… couldn't summarise them"*. The obvious suspect was the handover: 23 columns per record. It
was the wrong suspect, and it took direct measurement to see that.

Ollama's own log has the answer:

```
slot operator(): id 0 | task 0 | new prompt, n_ctx_slot = 16384, task.n_tokens = 155
ggml_cuda_compute_forward: ADD_ID failed
CUDA error: an illegal memory access was encountered
llama-server terminated  error="exit status 0xc0000409"
```

**A 155-token prompt crashed it.** `ADD_ID` is the expert-routing kernel this MoE model uses;
this is a CUDA-level fault on this GPU, twelve times in a ten-minute burst (09:50–10:00), and
it then recovered on its own. Direct calls at 14k, 47k, 117k, 211k and 351k characters — same
`num_ctx=16384`, same `keep_alive` — all answered normally, as did concurrent pairs. Nothing
about the register prompt caused it.

**What WAS ours:** after such a crash Ollama respawns `llama-server` on a new port and takes
5–14 s to answer again, while the retry backoff was 1 s then 2 s. All three attempts hit a
refused port, so a correct answer degraded into a fallback. The backoff now recognises a dead
runner and waits it out (`LLM_RUNNER_RESTART_WAIT_S`, default 10 s); a merely slow provider
keeps the short backoff. **CAVEAT-619**, and the demo mitigation if it recurs is to restart
Ollama — this is not something the code can repair.

### The cap then did real harm — and this is the part worth reading

The 12-column cap, invented for a cause that did not exist, produced a worse answer than the
width ever had. Asked *"which spaces are suitable for quiet focused work for a group of four?"*
the projection dropped `noiseProfile`, `quietestPeriod` and `seatCount`, and the system replied:

> The records do **not** contain any field that records whether a space is quiet or suitable
> for focused work.

That is the building denying its own data, in the confident register of a fact. Worse, the rows
counted **in code** — the RECORDED FACTS block, the whole point of which is that the figures do
not depend on the model — were taken *after* the projection, so the system's most authoritative
numbers were being computed from data it had just thrown away (**BUG-622, P1**).

Fixed by: counting the facts from the full rows before any projection; dropping only the
provenance stamps, which say where a row came from and never what it says; matching question
words on stems and prefixes so "quiet" reaches `quietestPeriod`; and raising the cap to 24,
where it trims nothing content-bearing in any register this building has. The answer is now
16 spaces, by floor, with seat counts and noise profiles.

### A count left to the narration is not a count

The probe's circulation case also moved, and the moving is the finding: *"on which floor pairs
is the step-free route slower than the stair route?"* answered **"nine"** one day and **"15 of
the 21 records"** the next, from the same twenty-one rows. Fifteen is true of the rows and false
of the question — six of those fifteen are same-floor routes, and a route from Level 0 to Level
0 has no stair alternative to be slower than.

Nothing had changed in the data. The comparison was simply never counted: `register_facts`
stated how many records and what statuses they carry, and left the arithmetic to the model,
which is the exact failure **BUG-581** was written to prevent, in a register it had not yet
reached. It is now computed in code (**BUG-624**) — and a row whose two endpoints are the same
place is excluded *and said to be excluded*, because six rows vanishing without explanation is
how a count becomes unauditable.

One thing worth keeping: the endpoint columns are found by their **values**, not their names —
two columns drawn from the same repeated vocabulary are the ends of a journey whatever a
register calls them. The first version required those values to be spelled with letters, which
passed every test written for it and found nothing at all in the live register, where a floor is
recorded as `3`. The test that pins it now uses the register's real shape.

Live: **"nine floor-pairs"**, listed correctly, in 32.3 s — down from 102.9 s.

## Afternoon: every floor instrumented, and questions about time and place

### The gap the old audit could not see

`scripts/data_coverage_audit.py` derives a sensor's floor from its URI text, so ~4,000 of
5,874 sensors land in a column called **F?** and no per-floor gap list can be trusted. A
sensor's floor is a fact the building states — sensor → space → floor — so
`scripts/floor_modality_matrix.py` now reads that instead. It placed all but **29** points on
a named floor and showed six gases — **CO, NO₂, PM1, PM10, formaldehyde, TVOC** — present on
exactly one floor: the one carrying the real instrumentation snapshot.

That asymmetry is invisible to a stakeholder. *"What is the NO₂ on floor 2?"* answered
honestly that nothing was measured, while the same question about floor 5 answered with a
figure, and nothing in either answer said why.

Closed by six entries in `config/saturation_modalities.yaml` — **config, not code**: no
building literal, no new adapter, units and bands taken from each measurand's declared
`physicalUnit` (BUG-609). `scope: floor` deliberately: per room these six would add ~1,400
points and slow every query, and one node per floor is how a multi-gas IAQ unit is actually
deployed. 36 points, 181,440 readings. *"Average TVOC on floor 3 today"* → **181.86 ppb**,
and the answer says it is a single sensor.

One honest limit: for a **readonly** role the k-anonymity floor (14 sensors / 7 spaces) still
refuses a one-sensor floor aggregate. That is the policy behaving as authored, not a defect.

### A question about time was answered from a single mean

*"How has the temperature on floor 3 changed over the last week?"* → **"No change data
available for floor 3 over the last week"**, from a week of readings that had been fetched,
clamped by policy and handed over. The only deterministic summary that existed was per
**floor**: one mean across the whole window, which cannot show a change within it (**BUG-626,
P1**). `summarise_periods` now buckets the same rows by hour, day or week — the bucket chosen
from the period the question names, else from the span — and states the change, the highest
and lowest period, with energy summed rather than averaged.

Its first output was wrong in a way worth keeping: *"electricity use increased by 639 kWh
(**+291.7%**) from the first day to the last day"* — a day that began mid-evening against a
day still running. A window almost always starts mid-bucket and ends now, and comparing those
edges reports a change in the **measurement window** as a change in the building (**BUG-627**).
Partial periods are now excluded from the comparison and named. Live:

> Electricity use increased by 1,181 kWh (**+55.0%**) from week 36 to week 37. … Week 38, with
> only 288 readings, is not comparable to a full week and is excluded from this comparison.

### Portability

`scripts/generate_record_documents.py` had `BUILDING = "Abacws Building"` as a **default**.
The `--building-name` flag existed, so it looked parameterised — but run for any other
building without it, the generator stamped one building's name across another's registers, in
headers that read as authoritative. It now takes the name from the active building's own
config and refuses to run without an owning authority rather than inventing one.

### Asking without knowing the building

*"Is it stuffy anywhere in the building?"* returned the row-budget refusal — *"that question
reaches 274 sensors"* — while *"which room is the stuffiest"* answered in one step from the
same data. The only thing between the two questions was a pattern that required the word
"room", so the building's ability to answer depended on the questioner already knowing how to
phrase it. That is the opposite of what this system is for.

It failed three times over, and all three had to go (**TODO-629**):

1. **Routing** — a condition word plus an existential scope ("is it *stuffy* *anywhere*") is a
   ranking question. Claimed wherever the classifier puts it, because it was variously called
   `capability`, `analytics` and — for *"is it too warm anywhere right now?"* — `compliance`,
   which answered **"No question was provided."** after 116 seconds (that prompt defect is
   **BUG-630**, open: routing this question away hides the symptom, not the fault).
2. **Stage** — the capability intent is assigned *after* the parse stage runs, so the same
   guard is needed inside the concept-stage rule.
3. **Compilation** — "anywhere in the building" was recorded as a term the compiler could not
   map, which made the query unexecutable and asked the user to *"rephrase or drop that
   part"*. It is not an unresolved place: it is the **absence** of a place, which is already
   this lane's default scope. Asking someone to drop the only word that said "look everywhere"
   is the wrong half to drop. The check that did this held `^anywhere$` — the bare word only —
   and now one function owns the decision for the anchor and the unmapped list alike, taking
   the building's own name from its config.

All first-pass, live:

| question | answer |
|---|---|
| Is it stuffy anywhere in the building? | Room 5.59, **1113.8 ppm** CO₂, ranked — "stuffy scored as above co2 against the 420–1500 band" |
| Is there anywhere quiet I can work? | Room 0.18, **57.19 dB**, minimised |
| Is it too warm anywhere right now? | Room 5.26, **25.04 °C** |

It resolves the lay term to a quantity, ranks every room, names the worst with its figure, and
states the assumption it scored on.

### 204 ppm of carbon monoxide

The first answer from the new gas sensors read **204.00 ppm**. The building declares carbon
monoxide's ordinary range as 0–5 ppm; 200 ppm is a level a person evacuates a building over
(**BUG-635, P1**). Every gas here writes to `iaq_data.voc`, and the publisher picked its value
range by **column name** — so carbon monoxide inherited the range for volatile organic
compounds. A narrow table's column names a family, not a quantity; only the uuid names the
quantity.

Each point now carries its own band, read from the ontology's `typicalMin/typicalMax`, and the
publisher prefers it over the column default (2,587 of 2,844 points; a class declaring no
measurand keeps the default rather than being guessed at). The 13,818 rows published during
the mis-ranged window were deleted so no average carries them. Live: **2.60 ppm**.

And the question could not reach that sensor at all until `carbon_footprint`'s bare lay term
**"carbon"** stopped claiming it and routing it to an electrical energy sensor (**BUG-636**) —
the same collision as the sustainability register's (BUG-625), one layer down.

### The data is placeholder data, and no answer calls it fake

User decision: these readings stand in for the building's own feed and are replaced wholesale
at connection time. So `· simulated`, `declared synthetic`, and the
`_**Synthetic demonstration record**_` banner on 38 registers described the deployment **stage**
— and reached stakeholders as statements about the building. Removed from the chip, the
evidence record, the asset-state lane, the locked-capability message, **1,610 point labels**
(a label is quoted verbatim in answers) and the generators that write them.

**What did not change, and is asserted by test:** the `isSimulated` triples, the `simulated:`
front matter and the `synthetic` flag on a provenance tag all stay, so the declaration is still
where an auditor reads it. The system still never invents a figure, still names each source,
and still reports an absence as an absence.

## The rehearsal, and what only a rehearsal finds (2026-09-17)

All 44 demo-script questions asked in one pass. Two privacy refusals are the intended answers;
one question genuinely failed and one carried a warning that should never have reached a
stakeholder.

**"Which rooms in the building are the stuffiest right now?"** → *"I couldn't map part of your
request (stuffiest)"*, while the same question with **stuffy** compiled cleanly. Two layers of
vocabulary, each complete only in the plain case: the compiler's lay-term hints list "stuffy"
and no inflection, and the whole-building scope test knew "anywhere" but not a bare plural
space noun, so the next attempt failed on **"rooms in the building"**. People ask for the
extreme far more often than the plain adjective (**BUG-640**). The reduction now lives in code
— `-iest/-ier/-est/-er` → the listed form — and only resolves to a modality the building
actually has, so translating is not guessing. Live: **Room 4.02 at 800.6 ppm**, ranked.

**Room temperatures of up to 526 °C** sat in the store (**BUG-641**), surfaced as *"the
recorded temperature value (259, 281, 292) is outside the range this quantity can take"*
riding along on a tap-water answer. The band guard was doing its job. Deleted on the
**physical** bound, never the typical one: 3,468 air rows and 48 water rows. Values merely
above the ordinary range were left alone — 9–20% of several tables sit there, and that is
variation, not corruption. `temperature_data` now spans 18–26 °C.
