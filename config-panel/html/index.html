    Config backup & restore

    Download a portable snapshot of console-managed config (data sources, DB connections, role access, toggle-state). Secrets (.env) are never included. Restore validates every file and writes it back; a recreate applies registry reloads.

    Environment (.env)

    The root .env is the backend source of truth. Secrets are masked (••••) — leave them untouched to keep the current value, or type a new one to overwrite. Env is read at boot, so saved changes apply after an orchestrator restart. Requires system:admin.

    Database connections

    A sensor's UUID → ref:storedAt bldg:<key> selects the connection used to fetch its time-series. Credentials are stored in .env; the connection entry lives in database_registry.custom.yaml (your curated registry is never rewritten). Applies after a restart.

    real = a source this building declares as measured data   synthetic = tables generated for this demo. All time-series values are demo/simulated data — the badge reflects the origin of the data source, not that any readings are live.

    This console controls what OntoSage can answer and how. Here is the mental model and the common flows.

    The core idea — a data source has two halves

    OntoSage answers by (1) finding a sensor + its UUID + where it's stored in the ontology (SPARQL against GraphDB), then (2) fetching that sensor's time-series from a database. A question is only answerable when both halves exist — which is why enabling a synthetic source writes Brick triples and database rows.

    Tabs at a glance

    • Overview — system state: provider, enabled sources, health.
    • Data Sources — toggle synthetic sources. Off = related questions are politely declined ("enable X to unlock"). Regenerate writes fresh synthetic data; Reset (clean slate) switches everything off for a repeatable demo.
    • Ask (test) — ask a question and see the answer, the provenance chips (which systems produced it), and the routed intent. Use it to prove a toggle worked.
    • AI & Models — pick the LLM provider/model and embedding backend.
    • Settings (.env) — raw backend environment (secrets masked).
    • Databases — connect external databases and register their sensors.
    • Users & Access — accounts, roles, and which sources each role may query.
    • Health — live status of every dependency.

    Demo flow — unlock a capability in four steps

    1. On Ask, ask "what is the noise level on floor 5?" — it's declined (source off).
    2. On Data Sources, find Acoustic / Noise Sensing, click Regenerate, then toggle it on.
    3. Back on Ask, ask again — now a real answer with an "Acoustic Sensing System" provenance chip.
    4. Finish with Reset (clean slate) to switch everything off.

    Connect an external database — two steps

    1. Add connection (Databases tab) — host + credentials, stored in .env.
    2. Register sensors — describe the DB's sensors (points form, CSV, or Brick TTL) so SPARQL can find them. Each sensor's real UUID + ref:storedAt bldg:<key> routes its queries to this DB. Applies immediately (cache flushed).

    Switching the AI model

    On AI & Models, pick a provider (OpenAI / local Ollama / Ollama Cloud) and a model. For local Ollama, click Fetch installed to list models actually installed. Save writes .env; then recreate the orchestrator to apply it (clients are built at boot). Switching the embedding provider changes vector dimensions (384 ↔ 1536) and invalidates the existing Qdrant index — you must re-index.

    Roles & access

    On Users & Access, each role can be limited to specific data sources. A role left unconfigured is unrestricted (opt-in control). admin always has full access. Changes apply immediately.

    Sign in

    Sign in with an admin account. Username or email both work — the same credentials as the chat interface. Non-admin accounts can use chat on port 3000.
